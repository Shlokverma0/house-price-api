# 🏠 House Price Prediction API — 4-Layer Architecture

A production-style FastAPI service that predicts house prices using a
Multiple Linear Regression model trained on the Kaggle
[Housing Prices Dataset](https://www.kaggle.com/datasets/yasserh/housing-prices-dataset),
built with a clean **4-layer architecture** for maintainability and testability.

---

## 🏗️ Architecture

```
Request
   │
   ▼
┌─────────────────────────┐
│ Layer 1: Routes         │  app/routers/predict.py, app/main.py
│ Receives HTTP requests, │  Only knows HOW to talk HTTP, not HOW to predict.
│ returns HTTP responses  │
└───────────┬─────────────┘
            ▼
┌─────────────────────────┐
│ Layer 2: Schemas         │  app/schemas/house.py
│ Defines & validates the  │  Pydantic models: field types, ranges, errors.
│ shape of request/response│
└───────────┬─────────────┘
            ▼
┌─────────────────────────┐
│ Layer 3: Services        │  app/services/prediction_service.py
│ Business logic: turns    │  Applies the SAME preprocessing (imputer) used
│ input into a prediction  │  at training time, then calls the model.
└───────────┬─────────────┘
            ▼
┌─────────────────────────┐
│ Layer 4: Models/Data      │  app/models/model_loader.py
│ Loads & holds the .pkl    │  The only layer that touches joblib directly.
│ artifacts                 │
└───────────────────────────┘
```

**Why this matters:** each layer has exactly one job. Routes don't know how
prediction works; services don't know about HTTP; the model loader doesn't
know about validation rules. Swap the model storage (e.g. to S3) and only
`model_loader.py` changes — nothing else in the app is touched.

```
house-price-ml-api/
├── app/
│   ├── main.py                    # FastAPI app, CORS, startup, health/root routes
```

## ⚙️ Setup

```bash
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

Kaggle authentication is required for `train.py` (one-time setup):
https://github.com/Kaggle/kagglehub#authenticate

---

## 🧠 Step 1 — Train the Model

```bash
python train.py
```

This will:
1. Download `Housing.csv` via `kagglehub` (`yasserh/housing-prices-dataset`)
2. Keep only the 5 features used by this API: `area`, `bedrooms`, `bathrooms`,
   `stories`, `parking`
3. Split into train/test (80/20)
4. Fit a `SimpleImputer` (mean strategy) **on the training set only**, to
   avoid data leakage, and apply it to both train and test
5. Train a `LinearRegression` model
6. Print MAE, RMSE, and R² on the test set
7. Save: `house_model.pkl`, `house_columns.pkl`, `house_imputer.pkl`,
   `house_data_clean.csv`

> The same imputer is reused at inference time (Layer 3), so a missing
> field is handled the same way it was during training.

---

## 🚀 Step 2 — Run the API

```bash
uvicorn app.main:app --reload
```

Open the interactive docs:
```
http://127.0.0.1:8000/docs
```

### Endpoints

| Method | Path       | Description                              |
|--------|-----------|--------------------------------------------|
| GET    | `/`        | Basic "API is running" message            |
| GET    | `/health`  | Returns 200 only if the model loaded OK   |
| POST   | `/predict` | Accepts house features, returns price     |

### Example request

```json
POST /predict
{
  "area": 7420,
  "bedrooms": 4,
  "bathrooms": 2,
  "stories": 3,
  "parking": 2
}
```

### Example response

```json
{
  "predicted_price": 8345120.5,
  "currency": "INR"
}
```

Invalid input (e.g. `"area": -500`, `"bedrooms": 0`) returns a `422`
Unprocessable Entity with details on which field failed validation.

---

## 🧪 Step 3 — Run Tests

```bash
python -m pytest test_api.py -v
```

Covers: root/health checks, a happy-path prediction, and rejection (422) of
negative area, zero bedrooms/bathrooms, negative parking, and missing fields.

## 🌐 Deploying (e.g. to Render)

- **Build Command:** `pip install -r requirements.txt`
- **Start Command:** `uvicorn app.main:app --host 0.0.0.0 --port $PORT`
- Make sure `house_model.pkl`, `house_columns.pkl`, and `house_imputer.pkl`
  are committed to the repo (or generated by running `train.py` as part of
  the build step) so the deployed server can load them at startup.

## 📌 Notes for the report

- **Model:** Multiple Linear Regression
- **Features:** `area`, `bedrooms`, `bathrooms`, `stories`, `parking`
- **Target:** `price`
- **Preprocessing:** missing values handled via `SimpleImputer` (mean),
  fit only on the training split to prevent data leakage
- **Architecture pattern:** 4-layer separation of concerns
  (Routes → Schemas → Services → Model/Data)
